# Plan — SBOMs and signed provenance for framework and app releases (#1615)

Planning record for issue [#1615](https://github.com/autumn-foundation/autumn/issues/1615).
Written before implementation; kept as the design rationale for the shipped slice.

---

## 1. Brainstorming — every option considered

**Where does the SBOM come from?**

| # | Option | Verdict |
|---|---|---|
| B1 | `cargo cyclonedx` / `syft` invoked from CI YAML | Rejected — logic lives in untestable YAML, and the "does it match the tagged source?" gate degenerates into "the thing that generated it agrees with itself". |
| B2 | Hand-rolled generator inside a CI shell script | Rejected — same untestability, plus a second parser of `cargo metadata` nobody maintains. |
| B3 | **`autumn sbom` subcommand in `autumn-cli`** | **Chosen.** Pure Rust, unit-testable, and the same binary is already installed in the scaffold's builder *and* runtime image — so one implementation serves the framework gate (AC1), the app image (AC4) and the "what's in this binary" query (AC3). |
| B4 | A build-script that bakes the SBOM into every autumn app | Rejected — forces a framework-wide build cost on apps that never asked for it, and `#1242` already owns runtime build-info exposure. |

**How does a binary report its own crate versions with no source tree (AC3)?**

| # | Option | Verdict |
|---|---|---|
| B5 | Ship `sbom.json` beside the binary | Rejected — the AC explicitly says *no access to the source tree or lockfile*; a sidecar file is trivially separable from the binary it describes. |
| B6 | `--version --verbose` printing a `build.rs`-embedded list | Rejected — reinvents a de-facto ecosystem standard, and only covers apps that regenerate `build.rs`. |
| B7 | **`cargo-auditable`'s `.dep-v0` section + `autumn sbom --binary`** | **Chosen.** The issue's own gap analysis names it. The data is *inside* the binary, survives `docker cp`, and is the format `cargo audit bin` already reads — so autumn interoperates rather than inventing. |

**How is the Tailwind download in the scaffold Dockerfile made verifiable (AC4)?**

| # | Option | Verdict |
|---|---|---|
| B8 | `curl` + hardcoded SHA-256 ARGs per architecture | Rejected — two digests to hand-maintain per Tailwind bump; a version bump with a stale digest breaks every scaffolded build with an opaque error. |
| B9 | `curl` + fetch `sha256sums.txt` + `sha256sum -c` in shell | Rejected — a third, untested copy of logic `setup.rs` already implements and tests. |
| B10 | **Call `autumn setup` (already installed in the builder stage)** | **Chosen.** Deletes the unverified `curl` *and* the arch-detection shell entirely, and routes the download through the SHA-256-verifying, unit-tested `setup.rs` path the issue itself points at. Dev loop and production image now pin the same Tailwind version. |

**What attests the artifacts (AC2)?**

- B11 GPG-signed detached signatures + a published key — rejected: key custody is explicitly out of scope.
- B12 Sigstore `cosign` directly — rejected: another binary to install and pin.
- B13 **`actions/attest-build-provenance` (keyless SLSA/Sigstore, `gh attestation verify`)** — chosen: zero key custody, one documented verification command, and out-of-scope note in the issue permits "default keyless CI flows" only.

## 2. Reverse brainstorming — how could this ship and still be worthless?

| # | Failure mode | Mitigation in this slice |
|---|---|---|
| R1 | SBOM is generated by the release job, so it *always* matches — the gate proves nothing. | `autumn sbom --verify` regenerates from the checked-out source and compares semantically; `scripts/check-sbom.sh` additionally asserts the SBOM's root version equals the workspace version **and** the pushed tag. A hand-edited or stale SBOM fails. |
| R2 | SBOM is non-deterministic (UUID serial number, timestamp), so `--verify` can never pass. | No `serialNumber`, no `metadata.timestamp`. Components sorted by `(name, version, purl)` and de-duplicated by `bom-ref`. A dedicated test asserts byte-identical output across shuffled inputs. |
| R3 | Attestation exists but nobody can verify it, or the doc's command is wrong. | AC5 doc gives the exact `gh attestation verify` invocation for both surfaces, plus the *negative* case (tamper a byte → verification fails) so the reader proves the check is real. |
| R4 | The image carries an SBOM that doesn't describe the binary in it. | The SBOM is generated in the **builder** stage from the same source tree that compiled the binary, and the binary independently carries `.dep-v0`; the doc shows cross-checking the two. |
| R5 | `cargo-auditable` silently no-ops and `--binary` reports nothing, unnoticed. | `autumn sbom --binary` fails loudly with a distinct error when the section is absent, naming `cargo-auditable` as the fix. |
| R6 | Existing apps break: `--locked`/toolchain surprises in the scaffold Dockerfile. | SBOM generation in the image does **not** pass `--locked` (only the framework gate does), so a stale app lockfile still builds. |
| R7 | The whole feature is CI-only and rots because nothing tests it. | Workflow/template content is asserted from Rust integration tests (`supply_chain.rs`), so a regression fails `cargo test`, not just a release six weeks later. |
| R8 | Provenance attested for the *archive* but the release also carries unattested assets. | `release.yml` attests every file it uploads; `cli-release.yml` attests every per-target archive **and** its `.sha256`. |
| R9 | `autumn sbom --binary` only works on Linux ELF, so a macOS developer sees a confusing failure. | Decoder handles ELF (32/64, both endiannesses) and Mach-O (thin + fat); anything else returns an explicit "unsupported object format" error rather than "section not found". |

## 3. Six thinking hats

**⬜ White (facts).** Today: `release.yml` uploads a body only; `publish-gate.yml` produces `RELEASE_NOTES.md` + `release-tag.txt`; no workflow requests `attestations: write`; `grep -ri sbom` over the repo returns nothing. `autumn-cli/src/setup.rs` already downloads and SHA-256-verifies Tailwind; `templates/release/Dockerfile.tmpl` `curl`s the same binary with no verification. `flate2` and `serde_json` are already in `Cargo.lock`, so the decoder adds no new transitive dependency.

**🟥 Red (instinct).** The riskiest-feeling part is not the SBOM — it is touching the release train. A mistake here is discovered at tag time, when it is most expensive. Instinct says: make every new gate *fail closed but fail early*, and put the new machinery behind a script that can be run by hand before a tag.

**⬛ Black (what goes wrong).** Attestation steps need `id-token: write`; adding it to `release.yml` widens a privileged `workflow_run` workflow — keep `contents: read` everywhere it is enough and grant the new scopes only on the jobs that attest. `cargo install cargo-auditable` adds builder-stage time to every scaffolded image. `RUSTC_WORKSPACE_WRAPPER` only instruments workspace members — correct here, but must be commented so nobody "fixes" it to `RUSTC_WRAPPER` and blows the dependency cache.

**🟨 Yellow (upside).** One `autumn sbom` implementation covers four ACs. The Tailwind fix *removes* code. Scaffolded apps get provenance without opting in — which, per the gap analysis, no mainstream framework does.

**🟩 Green (creative).** `--verify` reporting a component-level diff (missing / extra / version drift) rather than a byte-diff makes the gate's failure message actionable. Emitting the SBOM into the image at a predictable path (`/usr/share/autumn/sbom.cdx.json`) plus an OCI `org.opencontainers.image.*` label means scanners find it with no autumn-specific knowledge.

**🟦 Blue (process).** Strict red → green → refactor per slice, in this order, so each slice's gate is provable before the next depends on it:
1. `autumn sbom` core (metadata → CycloneDX, determinism, verify).
2. `autumn sbom --binary` (object-file decoder).
3. Scaffold Dockerfile: verified Tailwind, auditable build, in-image SBOM.
4. Scaffold deploy workflows: image provenance + SBOM attestation.
5. Framework release train: SBOM asset, `check-sbom.sh` gate, attestations.
6. `docs/guide/supply-chain.md` + cross-links.

| AC | Artifact |
|---|---|

| AC5 "Verify what you're running" doc | `docs/guide/supply-chain.md`, linked from `deployment.md` and `release-checklist.md` |
