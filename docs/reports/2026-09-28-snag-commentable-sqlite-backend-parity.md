# 🪝 Snag: `#[commentable]` hard-delete had never run against SQLite — negative result, coverage gap closed

## 🎯 Charter

A SQLite-backend developer relying on `#[commentable]`'s freshly-merged
hard-delete cross-record-cascade refusal (issue #2275 / PR #2983, merged the
day before this session) — data-correctness / documented-claim tour, 90
minutes.

`docs/guide/commentable.md` states plainly: *"Both backends are supported."*
But `autumn/tests/integration/commentable.rs` — described in that same doc as
*"the canonical evidence"* — is written directly against `AsyncPgConnection`
and `testcontainers_modules::postgres::Postgres`; every behavioural test in
it needs Docker. `.github/workflows/ci.yml`'s `sqlite-runtime` job names
~30 `sqlite_*` test targets by hand, and none of them mention
`comment`/`commentable`. So the claim of backend parity for this feature —
including the brand-new #2275 refusal, which exists specifically to stop a
hard delete from silently corrupting a comment counter — had never actually
been exercised against the second backend the docs say it supports.

This is a different angle from the open tracking issue for SQLite gaps
(#2539): that issue's item 5 credits `commentable.rs`'s `ph(n)` placeholder
fork as *already solving* the Postgres-only-raw-SQL hazard, and cites it as
the pattern other modules should copy. Nobody had actually run the module
against SQLite to check that claim empirically — #2539 is about other
modules following commentable's pattern, not about verifying commentable's
own pattern works.

## 🪝 Session journal

1. Read `docs/guide/commentable.md` and `autumn/src/commentable.rs` end to
   end, building a claims inventory. The module turned out to be unusually
   well-hardened against exactly the bug classes worth probing: a
   `RECURSION_GUARD`-bounded recursive CTE handles a self-referencing or
   cyclic `parent_id` without hanging; `ids` are deduplicated by shallowest
   depth *before* being used as a counter delta, specifically to avoid a
   documented cyclic-data counter-corruption hazard; the row-lock clause
   (`FOR NO KEY UPDATE`) is already `cfg`-gated empty under `sqlite`,
   citing the exact precedent bug (#1996) this session went looking for;
   and the hard-delete's returned count is `ids.len()` (the walk's own
   count), not the database's `execute()` affected-row count — sidestepping
   a second SQLite-specific hazard a stale test comment in the same file
   documents (SQLite's `changes()` excludes FK-cascade-removed rows).
   Every hypothesis generated by reading the code turned out to already be
   deliberately handled, each with a comment citing the issue it came from —
   this is not a module that yields findings to code review.
2. Confirmed empirically (not by inference) that the feature's only live-DB
   coverage is Postgres-only: grepped `ci.yml`'s sqlite-runtime job's named
   test list (30 targets, zero commentable-related) and confirmed
   `docker info` fails in this sandbox, so the existing Postgres suite
   could not be run here either.
3. Per charter step 3 ("drive it — with structured malice"), wrote and ran
   an actual SQLite-backed probe rather than filing anything from the
   reading above (banned practice: "speculative code-reading filings").
   Added `autumn/tests/sqlite_commentable.rs`, mirroring two scenarios from
   the Postgres suite against a real in-memory SQLite connection (no
   Docker): the plain hard-delete-removes-a-subtree path, and specifically
   the new #2275 cross-record-graft refusal (raw-SQL grafts a reply from
   one record's subtree onto another, then asserts the hard delete returns
   422, names the offending reply, and leaves all 4 rows and both counters
   untouched; then repairs the edge and confirms the delete succeeds).
4. First run: both tests failed. Both failures were in my own test
   scaffolding, not the framework — worth recording since a scratch probe's
   own bugs are exactly the kind of noise the hard gate exists to catch
   before filing anything:
   - `seed_user`/`seed_hard` held a checked-out connection open across a
     nested `pool.get()` call, self-deadlocking a pool sized to 1
     (`Timeout(Wait)`). Fixed by scoping the connection to a block.
   - Both tests shared one `sqlite://file:sqc_commentable?mode=memory&cache=shared`
     database name, so run together in one binary the second test's
     `CREATE TABLE` collided with the first's ("table … already exists").
     Fixed by giving each test its own in-memory database name.
5. Re-ran: both tests pass, deterministically, 4/4 across repeated runs
   (rate discipline applies to a negative result too — see Reproduce).
   `cargo clippy -p autumn-web --features "sqlite,test-support" --test
   sqlite_commentable -- -D warnings` is clean; `cargo fmt` applied.

## 💥 Result: negative — the claim holds, and the gap is now closed

**No bug found.** The #2275 hard-delete cross-record-cascade refusal, and
the plain hard-delete-removes-a-subtree path underneath it, behave
identically against a live SQLite connection: same 422, same message naming
the offending reply, same "nothing removed" guarantee, same success and
counter state after the edge is repaired. `docs/guide/commentable.md`'s
"Both backends are supported" claim holds for this path, empirically, for
the first time — the only prior evidence for it was that the SQL happened to
compile under the `sqlite` feature flip, which is a much weaker claim than
"runs and behaves the same."

This is reported as a session finding rather than silence for the reason the
charter gives for a session report: "toured and solid" is only worth
something because it wasn't inflated — and this specific tour (this exact
feature, this exact fix, on this exact backend) had never been run before,
by anyone, so "solid" was previously an assumption resting on the SQL
compiling, not a measurement.

**Per the charter's outcome #4 (Test-gap PR)**, the probe is committed as a
permanent regression test rather than discarded: `docs/guide/commentable.md`
claiming backend parity is exactly the kind of claims-inventory item the
charter asks to be encoded as an executable check, and #2539 (the open
SQLite-gaps tracking issue) is evidence nobody else was going to add this
particular coverage soon — its own item 5 treats `commentable.rs` as a
*model* for other modules to copy, without having verified the model itself
executes correctly.
